Prototype rationale

Why it works this way

Five decisions that shape search, the library, and the day-to-day experience for a non-engineer building an automation. Change any of them and the prototype changes shape.

01 Search takes a job, not a noun

Business builders don't know that "delivery slot scheduling" is the name of the thing they need. The input is phrased I want to… and matches against an intent list curated per listing — the phrases real people use for that capability — before it ever looks at the title.

Every result shows why it matched. That single line does more for trust than a relevance score ever will, and it teaches the vocabulary: after two searches, people start using your domain terms.

  • Facets stay, but they narrow a ranked list rather than replace it.
  • Intents are content owners' work, not the search team's — treat them as a required publishing field.

02 "Can I actually use it?" is a search result attribute

For a business builder the blocking question isn't whether a capability exists — it's whether they can use it, with their data, in their region, this week. So access state sits on the row itself, and Fastest to get access is a first-class sort.

Region is set once in the header and everything downstream respects it. Anything unavailable where you're building is dimmed and labelled rather than hidden, so people learn the estate instead of being quietly denied.

03 One metadata spine, four listing types

APIs, agents, MCP tool servers and data products share the same spine — owner, domain, maturity, regions, data class, access path, usage. Only the proof of quality differs, and that's the type-specific block in the detail panel:

  • API — p95 latency, uptime, protocol, version
  • Agent — autonomy level, human checkpoint, eval pass rate
  • Tool server — the tools it exposes, scopes, transport
  • Data product — freshness, volume, shape

Colour identifies type the way a transit line does — consistently, everywhere, and never reused for status.

04 The library holds kits, not just bookmarks

Nobody solves a real job with one listing. Kits are curated bundles that already work together, with the composition written down — "this agent calls that API, reads that stream". They're the fastest path from search to something running, and they're where your platform team encodes the paved road.

The library also carries access requests as visible, chase-able state. Requesting access is the moment most internal catalogues lose people.

05 What's real and what's staged here

  • Staged: semantic ranking is a curated intent + synonym map, not embeddings. Good enough to test the interaction, and honestly cheap enough to ship as v1 while you build the real index.
  • Staged: the 23 listings, usage figures, and Halden Group itself are invented but structurally realistic.
  • Real: the metadata model, facet set, ranking inputs, access states and page flows are what you'd implement.
  • Missing on purpose: publishing/onboarding flow, chargeback, versioning and deprecation comms, and the developer-facing "try it" console — all needed, none of them the thing you asked to figure out first.
